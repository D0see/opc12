OPC12 — SUPPORT DE PRESENTATION ORALE
Projet EcoGarden & co

Objectif : presenter l'API, ses choix de conception et ses limites avec transparence.
Duree totale : 30 minutes (15 min de presentation, 10 min de discussion, 5 min de debrief).


1. PRESENTATION DES LIVRABLES — 15 MINUTES

0:00–1:00 | Introduction

« Bonjour, je suis Lucie et je vais vous presenter OPC12, une API developpee avec
Symfony et PHP. Elle repond a trois besoins principaux d'EcoGarden & co : gerer les
comptes utilisateurs, diffuser des conseils de jardinage en fonction du mois, et
afficher une mesure de temperature associee a un code postal. »

L'API s'appuie sur Symfony 7.4, Doctrine ORM et une base de donnees relationnelle.
Les donnees sont exposees en JSON. Les responsabilites sont reparties entre les
controleurs, les services metier, les repositories, les entites et des DTO.


1:00–4:00 | Entites et modele de donnees

- User : compte de l'utilisateur. Il contient un identifiant de connexion, un mot
  de passe hashe, des roles et un code postal. Un utilisateur peut etre associe a
  plusieurs conseils.
- PostalCode : code postal numerique stocke sur cinq caracteres. Il relie un lieu
  aux mesures meteorologiques et peut etre partage par plusieurs utilisateurs.
- Tip : conseil de jardinage, avec un contenu, un auteur (User) et un ou plusieurs
  mois de validite.
- Month : mois reference par son numero et son libelle. L'association entre Month
  et Tip est plusieurs-a-plusieurs : un conseil peut concerner plusieurs mois et
  un mois peut proposer plusieurs conseils.
- WeatherMesurement : releve meteorologique avec une temperature, une date et un
  PostalCode. Plusieurs releves peuvent concerner le meme code postal.

« Ces entites traduisent les objets du domaine et leurs relations : le compte est
rattache a une zone, les conseils sont classes par mois, et les mesures sont
historisees par code postal. »

Les reponses passent par des DTO et des mappers afin de ne pas exposer directement
les entites Doctrine. Par exemple, la reponse meteo donne la temperature, la date
et le code postal ; la reponse utilisateur donne le login et le code postal.


4:00–7:00 | Routes et donnees exposees

Authentification et comptes :
- POST /api/auth : authentification ; retourne un jeton JWT en cas de succes.
- POST /api/user/create : creation publique d'un compte ; reponse 201 Created.
- PUT /api/user/{user} : modification d'un compte, reservee a ROLE_ADMIN ;
  reponse 200 OK avec les informations mises a jour.
- DELETE /api/user/{user} : suppression d'un compte, reservee a ROLE_ADMIN ;
  reponse 204 No Content.

Conseils :
- GET /api/tip/ : conseils du mois en cours ; reponse 200 OK.
- GET /api/tip/month/{monthNum} : conseils d'un mois de 1 a 12 ; reponse 200 OK,
  ou erreur de validation si le numero est hors limites.
- POST /api/tip : creation d'un conseil, reservee a ROLE_ADMIN ; reponse 201 Created.
- PUT /api/tip/{tip} : modification d'un conseil, reservee a ROLE_ADMIN ;
  reponse 200 OK.
- DELETE /api/tip/{tip} : suppression d'un conseil, reservee a ROLE_ADMIN ;
  reponse 200 OK actuellement.

Meteo :
- GET /api/weather-mesurement : releve du jour pour le code postal du compte
  authentifie ; reponse 200 OK.
- GET /api/weather-mesurement/{postalCode} : releve du jour pour un code postal
  indique ; reponse 200 OK.

« Les routes de meteo et de lecture des conseils necessitent elles aussi un JWT :
la configuration protege globalement les routes /api, sauf l'authentification et
la creation de compte. »


7:00–10:00 | Securite

- Le login est traite par le firewall JSON de Symfony et LexikJWTAuthenticationBundle.
- Les routes privees sont sans session et attendent un jeton dans l'en-tete
  Authorization: Bearer <jeton>.
- L'authentification et la creation de compte sont publiques.
- Les operations d'administration sur les utilisateurs et les conseils portent
  l'attribut IsGranted('ROLE_ADMIN').
- Les nouveaux utilisateurs recoivent le role ROLE_USER ; l'entite User garantit
  aussi ce role lors de la lecture de ses roles.
- Les mots de passe sont hashes avec le hasher de mots de passe Symfony.
- Les DTO d'entree sont valides avant l'appel aux services metier, notamment pour
  les champs obligatoires, la longueur et les numeros de mois.

« Le JWT permet de securiser une API sans maintenir une session serveur entre les
requêtes. L'autorisation complete l'authentification : etre connecte ne suffit pas
pour executer les actions reservees a un administrateur. »


10:00–13:00 | API meteo et cache

Le service meteo passe par une interface WeatherMesurerInterface et un adaptateur
WeatherBitWeatherMesurer, qui appelle Weatherbit pour obtenir la temperature
actuelle en France. Cette separation isole le fournisseur externe du controleur
et facilite un remplacement ou un mock du client.

Le service de mesure construit une cle de cache avec le code postal et la date
(format AAAA-MM-JJ). La valeur est obtenue via le pool de cache Symfony. En cas de
defaut de cache, le service cherche une mesure en base, puis appelle Weatherbit si
aucune mesure n'est trouvee ; le resultat est enregistre en base et place dans le
cache. Le cache applicatif est configure pour utiliser le systeme de fichiers par
defaut. Aucun TTL specifique n'est defini dans le code consulte.

« En pratique, la cle contenant la date cree une cle differente le jour suivant.
Cela ne signifie pas que l'entree du jour expire automatiquement : aucune duree de
vie n'est configuree explicitement dans ce service. »

Point de vigilance a connaitre avant la presentation : le service associe les
entrees aux tags "weatherMesurement" et "postalCodeMesurement:<code>", mais tente
d'invalider le tag correspondant directement au code postal. Ces tags ne sont pas
les memes ; cette invalidation ne cible donc pas les entrees etiquetees par le
service. Ne pas presenter l'invalidation actuelle comme un rafraichissement garanti.

Pour forcer un rafraichissement a la demande, une evolution possible serait une
route explicite reservee a ROLE_ADMIN (par exemple POST
/api/weather-mesurement/{postalCode}/refresh). Elle invaliderait le bon tag ou la
cle de cache, appellerait Weatherbit sans reutiliser l'ancienne mesure, puis
mettrait a jour la base et le cache. Il faudrait egalement definir une duree de
vie et une politique de limitation des appels au fournisseur.


13:00–15:00 | Codes HTTP et conclusion de la presentation

Rappeler le sens des principaux codes :
- 200 OK : requete traitee avec succes, avec une representation si necessaire.
- 201 Created : une ressource a ete creee.
- 204 No Content : requete reussie sans contenu de reponse.
- 400 Bad Request : donnees de requete invalides.
- 401 Unauthorized : authentification absente ou invalide.
- 403 Forbidden : utilisateur authentifie mais non autorise.
- 404 Not Found : ressource introuvable.
- 409 Conflict : conflit avec l'etat existant, par exemple un login deja utilise.
- 500 Internal Server Error : erreur inattendue cote serveur.

« Les actions de lecture et les modifications qui retournent une representation
utilisent 200 ; les creations utilisent 201 ; la suppression d'un utilisateur
utilise 204. Les validations des DTO et le numero de mois invalide sont exprimes
comme des erreurs 400. La creation d'un login deja pris est exprimee comme un
conflit 409. »

Le subscriber d'exceptions transmet maintenant le statut HTTP de l'exception
dans la reponse, en coherence avec le champ "status" du JSON. Les erreurs de
deserialisation JSON et les erreurs de validation metier (conseils, utilisateurs
et codes postaux) sont traitees comme des erreurs 400. Les erreurs inattendues
restent des 500 generiques.

Conclusion proposee :
« Le projet couvre les besoins principaux avec un modele de domaine lisible, une
API authentifiee, des routes metier et une integration meteo decouplee. Les
ameliorations prioritaires concernent la strategie d'expiration/invalidation du
cache et des tests d'API couvrant les statuts HTTP, les roles et les erreurs. »


2. DISCUSSION — 10 MINUTES

Question : Qu'est-ce qu'une API REST ?
Reponse suggeree :
« REST est un style d'architecture pour des services accessibles par des
ressources. Les ressources sont identifiees par des URI, les representations sont
transmises dans un format comme JSON, et les methodes HTTP indiquent l'action
attendue. Une API REST est generalement sans etat : chaque requete contient les
informations necessaires a son traitement. »

Question : Quels sont des exemples communs d'utilisation d'API REST ?
Reponse suggeree :
« Une application mobile qui consulte un catalogue, un site qui transmet une
commande, un service de cartographie, une API de paiement ou une application qui
recupere la meteo depuis un fournisseur externe. Ici, notre serveur interroge
Weatherbit pour obtenir une temperature. »

Question : Quels sont les verbes HTTP ?
Reponse suggeree :
« Les principaux sont GET pour lire, POST pour creer ou declencher une action,
PUT pour remplacer ou modifier une ressource, PATCH pour une modification
partielle, et DELETE pour supprimer. HEAD et OPTIONS ont aussi des usages
specifiques. Dans notre API, nous utilisons principalement GET, POST, PUT et
DELETE. »

Question : A quoi servent les codes de retour ?
Reponse suggeree :
« Le statut HTTP indique au client le resultat de la requete de facon standardisee :
succes, erreur du client, probleme d'authentification ou erreur serveur. Il permet
au client d'adapter son comportement sans devoir interpreter uniquement le texte
du message. Le corps JSON peut apporter des details, mais doit rester coherent
avec le statut HTTP reel. »

Question : Pouvez-vous justifier les codes de retour ou d'erreur utilises ?
Reponse suggeree :
« 201 indique qu'un utilisateur ou un conseil a ete cree ; 200 indique une lecture
ou une modification reussie ; 204 indique une suppression sans contenu. 400 est
adapte a des donnees invalides, 401 a une authentification manquante ou invalide,
403 a un utilisateur sans les droits necessaires, 404 a une ressource absente et
409 a un conflit comme un login deja pris. Un 500 doit etre reserve a une erreur
inattendue du serveur. Le subscriber transmet le statut HTTP de l'exception et le
repete dans le JSON. Les erreurs de validation et de JSON mal forme renvoient 400.
Ces comportements doivent etre couverts par des tests fonctionnels. »

Question : Qu'est-ce que le niveau de maturite de Richardson ?
Reponse suggeree :
« C'est une grille en quatre niveaux pour evaluer le degre d'adoption des principes
REST. Le niveau 0 utilise HTTP comme un simple tunnel. Le niveau 1 introduit des
ressources identifiees. Le niveau 2 utilise correctement les methodes et codes HTTP.
Le niveau 3 ajoute des liens hypermedia qui guident le client, souvent nomme
HATEOAS. Notre API se rapproche du niveau 2 avec des URI par ressource et des
verbes HTTP ; elle n'expose pas de liens hypermedia, donc elle n'atteint pas le
niveau 3. »

Question : Est-il facile de faire evoluer l'API ?
Reponse suggeree :
« La separation controleurs/services/repositories/DTO aide a faire evoluer le
projet sans concentrer toute la logique dans un seul endroit. L'interface meteo
permet de remplacer le fournisseur plus facilement. Pour limiter les ruptures,
on pourrait ajouter un versionnement comme /api/v1, documenter le contrat OpenAPI,
ajouter des tests contractuels et conserver la compatibilite des DTO. Le cache et
les erreurs standardisees sont aussi des points a consolider. »

Question : Quand et comment est renouvele le cache pour la meteo ?
Reponse suggeree :
« La cle est composee du code postal et de la date. Le lendemain, une nouvelle date
produit une nouvelle cle. Je ne peux pas affirmer que le cache du jour expire a une
heure precise : aucun TTL n'est defini dans ce service. Par ailleurs, l'invalidation
par tag actuelle ne correspond pas au tag postal utilise lors de l'enregistrement.
La duree de vie et le rafraichissement doivent donc etre clarifies et corriges. »

Question : Qu'auriez-vous pu faire pour forcer le rafraichissement du cache a la
demande ?
Reponse suggeree :
« Ajouter une route explicite et protegee, par exemple reservee a l'administrateur.
Elle invaliderait le tag exact du code postal ou la cle concerne, contournerait la
lecture de l'ancienne valeur, rappellerait Weatherbit, puis mettrait a jour le
releve en base et le cache. Je definirais egalement une limitation de frequence
pour eviter des appels excessifs au fournisseur. »


3. DEBRIEF — 5 MINUTES

Proposition de conclusion personnelle :

« Ce projet m'a permis de mettre en pratique la conception d'un modele de donnees,
la creation de routes REST, la securisation par JWT, la validation des entrees et
l'integration d'un service externe. J'ai aussi identifie des axes d'amelioration
concrets : fiabiliser les statuts HTTP d'erreur, mieux definir le cycle de vie du
cache meteo et renforcer les tests fonctionnels. »

Questions de recul a preparer :

- Que prioriserais-je pour une prochaine version ?
